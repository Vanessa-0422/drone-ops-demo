# 无人机即时配送 · 经营决策工具集

> ## ⚠ 本项目为个人作品集演示
>
> **仓库里不含任何数据文件。全部演示数据由 `scripts/gen_mock.py` 在构建时生成，
> 与任何真实业务、真实公司、真实地点无关。**
>
> 生成的数据只保留真实即时配送业务的**分布形态**（时段双峰、配送距离对数正态、
> 商家销量幂律、供给逐级损耗），量级锚定在一座大城市的规模上，
> 但每一个点位、围栏、商家名、覆盖率与经营数值都是虚构的。
>
> 底图为公开地图数据，其上的起降点、商圈边界、空域分区与候选点位均为脚本生成，不指向任何真实地点。

一套覆盖完整链路的经营决策工具：**开航前**回答开在哪、划不划算、先开哪，
**开航后**回答供给卡在哪一级、增长该推哪个杠杆，
上面再挂一个**决策入口**回答能不能赚、推进到哪、结论有多确定。

---

**入口是经营门户**（03）。它回答决策三问、列出全部能力的建设状态，并从这里跳进其余五个工具；
站点没有单独的工具集首页，根路径直接落到门户。

## 01 选址沙盘

### 解决什么业务问题

选址靠经验和现场勘查，供需分布无处可查；点位划定之后，这个位置到底能拿到多少单、
够不够养活一条航线，在圈定的那一刻答不上来。

### 核心功能

- **双侧热力**：需求（收货点）走电蓝色带，供给（商家）走暖橙色带，两层各有独立开关
- **真起讫配对**：订单计入的条件是「起点落在起飞点取餐圈内，且终点落在某个降落圈内」。
  归属口径是**最近点**，一单只归离它最近的那个降落点，不重复计
- **圈选即算**：拖起飞点、拖取餐半径、拖降落圈半径，订单池与整条测算链路实时重算
- **系统推荐降落点**：按需求密度与起讫聚类选点，禁飞区硬过滤，一键采纳进测算
- **时段刷选**：拖底部时段条筛小时区间，热力与订单池跟着变
- **只导图层的截图**：导出图只从地图图层取像素，左右两栏的经营数据在物理上进不了图

### 界面上能看到什么

三栏。左栏是数据概览与图层控制（热力、围栏、公网 POI 十类、空域限制三类、算法候选点）；
中间是地图，底部悬浮时段分布条；右栏在商圈列表与工作台之间切换。

进工作台后从上往下依次是：判决框（保本线 / 当前日均 / 月利润）、起飞点与降落点（可拖可改坐标）、
系统推荐降落点、七段决策链（圈内大盘订单 → 可承接率 → 可分配池 → 选择率 → 日均 → 收入 → 成本 → 利润）、
供给签约进度、场地租金，最后一个按钮带着当前情景跳到单元经济台。

### 技术要点

Leaflet + 热力插件，画布分 10 个 pane 控制叠放；订单起讫按起点网格聚合成
`{"i,j": [[终点纬, 终点经, 单量], ...]}`，查询时以起飞点为心枚举附近格子还原五元组；
射线法做多边形内外判定；截图走 canvas 手工合成，图层白名单加一道文字闸。

## 02 单元经济台

### 解决什么业务问题

场地租金在签约前拿不到精确报价，正向填成本算出来的盈亏不可信。
而「距转正还差多少、靠什么补」，如果没有一个能摆到谈判桌上的数，BD 就只能凭感觉谈。

### 核心功能

- **五段链路**：订单池 → 收入 → 成本 → 盈亏 → 转正，左边一列是每段的结论与测算逻辑，
  右边只显示当前段的明细
- **可承接率真的能构成**：商家覆盖三档 × 商品覆盖 = 可承接率，三个数在屏上对得上。
  商品覆盖乘的是**条件比率**（已上架 ÷ 已签可供给），不是「已上架 ÷ 圈内高销品」
  （后者分母含未签店，再乘一次会把商家覆盖算两遍）
- **成本反向倒推**：不正向填租金算盈亏，而由收益反推「这个单量下仍能保本的最大月租」。
  这个数是会动的：覆盖补上去、选择率提上去，上限跟着抬
- **保本线取真实解**：人力与设备都是阶梯量，利润对单量非单调，
  所以取**最后一段连续为正的起点**，首次穿零另标出来
- **敏感性沙盘**：租金 × 单量的利润率矩阵，当前场景在格子上标金框
- **逐点租金四模式**：固定 / 仅营业额提成 / 固定加营业额提成 / 固定加配送费提成
- **五年逐年推演**与按转正周期反推租金上限

### 界面上能看到什么

顶部是常驻的判决条（月亏或月利、保本线、还差多少、几年转正、可承受租金上限）。
中间左边五段结论列，右边当前段明细。底部是折叠的调参面板，按 A 到 I 分组，
固定参数单独收进一个折叠区，改任何一个数整页即时重算。

### 技术要点

测算引擎是全站唯一口径单源（`engine/ue_model.js`），由 `scripts/inject_ue.py` 注入到各页；
五年曲线的坐标文字与数据点走 HTML 绝对定位而不是 SVG，因为 `preserveAspectRatio="none"`
会把 `<text>` 与 `<circle>` 一起拉伸变形；反推租金上限用二分，判据是目标年当年利润不为负。

## 03 经营门户

### 解决什么业务问题

结论散在几个页面里各自重算，决策层没有一个统一入口；
更麻烦的是，同一个指标在不同页面上口径不同，答案就不同。

### 核心功能

- **结论三问**：能不能赚、推进到哪、结论确定性。三个数与副文案都由生成器现算写进数据文件，
  **页面不做业务计算**
- **逐商圈经济性**：订单池、可承接率、当前日均、保本线、缺口、月利润、可承受租金上限一行一个商圈
- **四支柱能力地图**：能力行可展开看实现方式、可行性与依赖
- **指标三态清单**：驱动结论的每个量标一种数据性质（实测 / 可推导 / 假定值）
- **里程碑编辑**：把进度条换成五格里程碑，点格子改进度，存本地

### 界面上能看到什么

顶栏一枚药丸写「判决刷新于」而不是「数据截至」，因为经营、开航、阻塞三块的数据日各不相同，
各自标在副题里。往下是公式条、结论三问三张卡、建设进度环与四个统计卡、
逐商圈经济性表、能力地图、行动与进度两列，最后是折叠的指标三态清单。

### 技术要点

两条纪律写在代码里：
**`pg` 与 `live` 是两个维度，不合并** —— 前者说这条能力对决策有多可用，后者说它有没有部署，
工具上线不让结论更可信，把 `pg` 打满会让门户传达「问题已解决」；
**迭代日志有数据但不渲染** —— 这是判断不是漏渲染，门户给决策层看，逐版缘由属于接手者读的内容。

## 04 商家 BD 工作台

### 解决什么业务问题

只知道覆盖率低，说不清是没签、签了没开通、开通了没上架，还是上架了没动销。
不同的卡点对应完全不同的动作，但报表上它们长得一样。

### 核心功能

- **供给四级漏斗**：圈内商家池 → 已签 → 已开通 → 有动销，逐级看损耗
- **商品四级漏斗**：圈内在售 → 已签可供给 → 已上无人机菜单 → 有动销
- **名单五视角**：全量 / 核心 / 配额 / 长尾 / 已签，每个视角对应一个当天的动作
- **预警只管「已签之后出问题」**：渠道回撤、零上架、已签零单三类逐家列出
- **今日事项**收敛成恰三张行动卡
- **经营概览**七段叙事：KPI 条、转化漏斗、三十天趋势、商圈榜、品类结构、激活链路、明细表

### 界面上能看到什么

两个视图切换。今日作业是左右两栏：左栏是指标达成进度、品类签约矩阵、今日三件事、预警；
右栏是商家名单（可排序、可搜索、行内展开）与商品名单。经营概览是七段自上而下的骨架，
每段带一句「这段回答什么问题」。

### 技术要点

图表全部内联 SVG 手画，不引图表库；空态刻意分两种：
「本商圈尚无已签商家，预警不适用」不同于「逐家检查过没发现异常」，
这两句在页面上不能长得一样。「待催上架」刻意**不作预警类型**：
门槛放开后八成以上的已签店都会命中，那不叫异常叫名单。

## 05 业务助手（无界面）

### 解决什么业务问题

一线每天要的不是报表，是一个数加一句能转述出去的话。
但同一个「保本线」有三种算法，答案能差三成；如果助手自己算，
它选哪一种取决于提问措辞，同一个人连问两次都可能不一样。

### 核心设计

- **把「怎么算」从助手身上拿走，只留「怎么说」**。两个助手与工具页共用同一份引擎
- **提示词分四层**（平台 / 助手 / 技能 / 会话），冲突判定写死在助手层，**会话层改不动口径**
- **取数脚本的返回自带口径说明**，助手要连口径一起转述
- **假定值必须标出来**。不标，等于把拍的数当成测的数往外说
- **红线用例管行为，锚点用例管数值**，不过就不出包
- 角色包六件：`role.json` `SOUL.md` `AGENTS.md` `TOOLS.md` `BOOTSTRAP.md` `HEARTBEAT.md`

这块没有界面，价值在结构不在聊天窗口，所以用目录、配置文件与用例把设计讲清楚，
不做假的聊天演示。完整说明见 [`agents/README.md`](agents/README.md)。

## 06 开航排期推演台

### 解决什么业务问题

实单样本太小不能当基准，跨城开航顺序只能凭经验排，排完无从复核；
而「这个点位划算」与「这个点位什么时候开始划算」是两个问题，混着说会得出错误结论。

### 核心功能

- **两个指标分开给，不合并成一个分数**：
  **静态账过线**问的是稳态水位下这个点位的月账能不能打正，是终局判断；
  **梯队转正**问的是从开航那天起多少个月之后当月利润转正，是过程判断。
  同一个点位可以静态账过线却在推演期内转不正，因为爬坡太慢
- **六十个月逐月推演**：覆盖爬坡 × 选择率爬坡两条曲线驱动，补贴按站龄递减
- **开航梯队五档**与**逐年排期**，受逐年产能闸约束，观察池不进排期
- **候选点位明细表**可排序，点一行出该点位的六十个月轨迹（当月利润与累计现金两条线）
- **地图视图**：候选点位按订单池定点径、按梯队定颜色，两个维度不合并
- 三档选择率并列，主档取中值

### 界面上能看到什么

排期页从上往下：三张判决卡、一段「两个指标不同源」的说明、开航梯队五档、
逐年排期甘特、候选点位明细表配轨迹卡、模型公式链六段、假定值一览（每条都标待校准）。
地图页是全域候选点位分布，右侧一栏是分城汇总与选中点位的轨迹。

### 技术要点

这条线与单城那条线**刻意不耦合**：取数范围与半径口径都不一样，混用会得出假的口径一致。
排期是白名单先落位再逐年贪心，白名单不过经济性闸也占一个产能名额，
占位不占名额会让产能闸形同虚设。

## 数据说明

### 数据边界

哪些是公开数据可以直接用、哪些必须生成，这条界线本身就是做数据产品的基本功：

| 数据 | 来源 | 本项目怎么处理 |
|---|---|---|
| 地图底图 | 公开地图服务 | 直接使用，署名常驻 |
| 公网 POI（餐饮、住宅、商场、学校） | 公开地图数据 | 按同一形态**生成同量级的点** |
| 起降点坐标 | 属业务数据 | **虚构生成** |
| 商圈围栏边界 | 属业务数据 | **虚构生成** |
| 空域限制分区 | 属公告数据 | **虚构生成**，不对应任何真实公告 |
| 订单起讫分布与时段 | 属业务数据 | **全部生成** |
| 商家签约状态、覆盖率、销量 | 属业务数据 | **全部生成** |
| 商家名与商品名 | 属业务数据 | **程序生成的占位名** |
| 成本科目、客单价、保本线 | 属业务口径 | **虚构取值** |

### 生成时怎么保留分布形态

只替换数值、不替换形状，这样热力图与排行榜看起来才是真实业务的样子：

| 维度 | 生成方式 | 为什么 |
|---|---|---|
| 订单时段 | 双峰分布，午高峰加晚高峰，晚峰更高 | 平铺的均匀分布一眼就假 |
| 配送距离 | 对数正态，中位数约 5 km，长尾到 15 km 以上 | 近距离占多数但长尾拉得很远 |
| 商家销量 | 幂律长尾 | 头部几家吃掉大半销量，这才是真实的商家结构 |
| 订单空间分布 | 几个商业核心加一串卫星热点，按距离衰减 | 真实城市的订单不是均匀铺开的 |
| 供给漏斗 | 逐级留存率不同，签约最难、动销最差 | 这个形状是这套业务的真问题 |
| 候选点位订单池 | 幂律 | 少数几个点吃掉大半，尾巴上一串怎么算都不划算 |
| 同城租金 | 跨度接近三倍 | 不是异常值，是真实商业地产的样子 |

量级锚在 `scripts/gen_mock.py` 的 `SCALE` 常量上：窗口六十天、全城四百三十四万完单、
客单价 46.7、出单商家一万三千六百家、餐饮 POI 四千二百、需求侧 POI 五千四百、免配占比 88.2%、
四个商圈、开航候选四座城市四十四个点位。**只锚定量级，具体数值仍由随机过程生成。**

固定随机种子，每次生成结果一致，演示可复现。换一组数据只要换 `--seed`。

### 生成器怎么跑

```bash
python3 scripts/gen_mock.py            # 生成到 site/data/
python3 scripts/gen_mock.py --seed 7   # 换一组数
```

生成完会打印一份自检：四个商圈的订单池与保本线、两条漏斗的逐级留存、开航梯队的分布。
形态不对一眼就看得出来。

## 技术栈

纯静态前端，原生 JavaScript，只有选址沙盘与排期推演台的地图页从 CDN 引 Leaflet，
其余页面零第三方依赖，图表全部内联 SVG 手画。数据生成只用 Python 标准库。

选这套的原因很直接：演示站要能被任何人在任何环境跑起来，不需要装环境、不需要构建步骤，
单个 HTML 文件双击就能看。

五个页面共用一份主题令牌（深色为基准，浅色只覆盖取值），共用一份测算引擎，
共用 `localStorage` 里的同一个主题键，切一次全站随身。
