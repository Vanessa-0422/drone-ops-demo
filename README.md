# 无人机即时配送 · 经营决策工具集

> ## ⚠ 本项目为个人作品集演示
>
> **仓库里不含任何数据文件。全部演示数据由 `scripts/gen_mock.py` 在构建时生成，
> 与任何真实业务、真实公司、真实地点无关。**
>
> 生成数据仅保留即时配送业务的**分布形态**（时段双峰、配送距离对数正态、商家销量幂律、
> 供给逐级损耗），量级锚定在一座大城市的规模上；点位、围栏、商家名称、覆盖率与
> 全部经营数值均为虚构。
>
> 底图取自公开地图数据，其上的起降点、商圈边界、空域分区与候选点位均由脚本生成，
> 不指向任何真实地点。

一套覆盖开航全周期的经营决策工具，按三个阶段组织：

- **开航前**　回答开在哪、是否划算、先开哪
- **开航后**　回答供给卡在哪一级、增长应推动哪个杠杆
- **决策入口**　回答能不能赚、推进到哪、结论确定性如何

---

**入口为经营门户（03）**：回答决策三问、呈现全部能力的建设状态，并由此进入其余五个工具。
根路径即门户。

在线演示一列是**站点内的路径**。本仓库按静态站发布（部署配置见 [`cloudflare-pages.md`](cloudflare-pages.md)），
部署后把站点域名拼在前面即可；本地跑起来后就是 `http://localhost:8080/sandbox/` 这一类地址。

六个工具由同一条测算链路贯穿：

```
圈定点位 → 圈内订单池 → 可承接率 × 选择率 → 日均单量
        → 月利润与保本线 → 可承受租金上限 → 开航排期
```

## 01 选址沙盘

### 解决什么业务问题

选址依赖经验判断与现场勘查，城市的供需分布缺少可查的载体。点位划定之后，
该位置能获取多少订单、是否足以支撑一条航线运转，在圈定的当下无法回答。

### 核心功能

| 功能 | 说明 |
|---|---|
| 双侧热力 | 需求侧（收货点）与供给侧（商家）分两层渲染，冷暖两条色带区分语义，各自独立开关 |
| 真起讫配对 | 订单计入的条件为起点落在取餐圈内且终点落在某一降落圈内。归属按最近点判定，一单只计入距其最近的降落点，不重复计数 |
| 圈选即算 | 起飞点位置、取餐半径、各降落圈半径均可拖拽，订单池与整条测算链路实时重算 |
| 候选点位推荐 | 按需求密度与起讫聚类生成候选，禁飞区作硬过滤，可一键采纳进入测算 |
| 时段筛选 | 底部时段条支持刷选小时区间，热力图与订单池随之更新 |
| 图层级截图 | 导出图仅从地图图层取像素，两侧栏的经营数据不进入图像 |

### 界面上能看到什么

**三栏布局。** 左栏为数据概览与图层控制，含热力、围栏、公网 POI 十类、空域限制三类与
候选点位；中栏为地图，底部悬浮时段分布条；右栏在商圈列表与商圈工作台两态间切换。

**工作台自上而下的信息层级：** 判决区（保本线、当前日均、月利润）、起降点配置
（位置可拖拽，坐标可直接编辑）、候选点位推荐、七段决策链、供给签约进度、场地租金，
末尾一个动作按钮携带当前情景参数跳转至单元经济台。

七段决策链的顺序为：圈内平台订单 → 可承接率 → 可分配订单池 → 配送方式选择率 →
日均单量 → 收入 → 成本 → 利润。

### 技术要点

地图基于 Leaflet 与热力插件，画布划分 10 个 pane 控制图层叠放次序。订单起讫数据按起点
网格聚合为 `{"i,j": [[终点纬, 终点经, 单量], ...]}`，查询时以起飞点为中心枚举邻近网格
还原五元组。多边形内外判定采用射线法。截图经 canvas 手工合成，图层白名单之外另设一道
文字过滤。

## 02 单元经济台

### 解决什么业务问题

场地租金在签约前无法取得精确报价，正向填入成本估算出的盈亏不具备参考价值。
同时「距转正的缺口有多大、由哪些杠杆补」若没有可量化的结论，商务谈判缺少报价依据。

### 核心功能

| 功能 | 说明 |
|---|---|
| 五段链路 | 订单池 → 收入 → 成本 → 盈亏 → 转正。左列逐段给出结论与测算逻辑，右区展开当前段明细 |
| 可承接率构成可验 | 商家覆盖三档 × 商品覆盖 = 可承接率，三个数值在同屏可相互验算 |
| 成本反向倒推 | 不正向填入租金计算盈亏，而由潜在收益反推当前单量下仍可保本的最大月租 |
| 保本线取真实解 | 扫描产能区间取最后一段连续为正的起点，首次穿零的单量另行标注 |
| 敏感性矩阵 | 租金 × 单量的利润率矩阵，当前情景在对应单元格高亮 |
| 逐点租金四模式 | 固定、仅营业额提成、固定加营业额提成、固定加配送费提成 |
| 五年逐年推演 | 并支持按目标转正周期反推租金上限 |

两处口径需要留意：

- **商品覆盖使用条件比率**，即已上架 ÷ 已签商家可供给。若改用「已上架 ÷ 圈内高销品」，
  分母含未签约门店，与商家覆盖相乘会导致商家覆盖被计入两次。
- **可承受租金上限是变量而非定值**，随商家商品覆盖与配送方式选择率变化。
  覆盖提升则上限随之抬高，这正是它可作为谈判锚点的原因。

### 界面上能看到什么

**master-detail 布局，顶部判决条常驻。** 判决条给出月度盈亏、保本线、距转正缺口、
转正周期与可承受租金上限五项结论。

主区左列为五段结论，右区展开当前选中段的明细。底部为可折叠的调参面板，参数按 A 至 I
分组，规格类固定参数单独收在一个折叠区内，任一参数变更后整页即时重算。

### 技术要点

测算引擎为全站唯一口径单源（`engine/ue_model.js`），经 `scripts/inject_ue.py` 注入各页
标记区。五年曲线的坐标文字与数据点采用 HTML 绝对定位而非 SVG 元素，因为
`preserveAspectRatio="none"` 会使 `<text>` 与 `<circle>` 随容器拉伸变形。
反推租金上限采用二分求解，判据为目标年度当年利润不为负。

## 03 经营门户

### 解决什么业务问题

结论分散在各个工具页中，决策层缺少统一入口。同一指标在不同页面口径不一致时，
同一个问题会得到不同答案。

### 核心功能

| 功能 | 说明 |
|---|---|
| 结论三问 | 能不能赚、推进到哪、结论确定性。三个数值与副文案由生成器现算后写入数据文件，页面不承担业务计算 |
| 逐商圈经济性 | 一行一个商圈，列出订单池、可承接率、当前日均、保本线、缺口、月利润与可承受租金上限 |
| 四支柱能力地图 | 按开航前、开航后、决策中枢、底座四类归置，能力行可展开查看实现方式、可行性与依赖 |
| 指标三态清单 | 驱动结论的每个量标注数据性质：实测、可推导、假定值 |
| 里程碑编辑 | 建设进度以五格里程碑记录，逐格可改，状态存于浏览器本地 |

### 界面上能看到什么

自上而下依次为：顶栏、公式条、结论三问三张卡、建设进度环与四张统计卡、
逐商圈经济性表、四支柱能力地图、行动与进度两列，末尾是可折叠的指标三态清单。

顶栏的时间标注为「判决刷新于」而非「数据截至」。经营、开航、阻塞三类数据的截止日期
各不相同，统一标注会掩盖差异，因此各自标在对应卡片的副题中。

### 技术要点

**建设进度与部署状态分列两个维度。** `pg` 表示该能力对决策的可用程度，`live` 表示是否
已部署。两者不合并的原因是：工具上线并不提升结论的可信度，若以部署状态填充建设进度，
门户会传达出「问题已解决」的错误信号。

**迭代日志存于数据但不在页面渲染。** 门户面向决策层，需要的是当前结论；
逐版变更缘由属于交接文档的范畴，两者受众不同。

## 04 商家 BD 工作台

### 解决什么业务问题

覆盖率偏低这一个结论，无法区分卡点在未签约、已签未开通、已开通未上架还是已上架未动销。
四类卡点对应的动作完全不同，但在汇总报表上呈现形态一致。

### 核心功能

| 功能 | 说明 |
|---|---|
| 供给四级漏斗 | 圈内商家池 → 已签 → 已开通 → 有动销，逐级呈现损耗 |
| 商品四级漏斗 | 圈内在售 → 已签可供给 → 已上无人机菜单 → 有动销 |
| 名单多视角 | 全量、核心、配额、长尾、已签、商品六个视角，各自对应一类当日动作 |
| 异常预警 | 仅覆盖签约之后的问题：渠道回撤、零上架、已签零单三类，逐家列出 |
| 今日事项 | 收敛为三张行动卡，避免作业面被待办淹没 |
| 经营概览 | 七段结构：KPI 条、转化漏斗、三十天趋势、商圈榜、品类结构、激活链路、明细表 |

### 界面上能看到什么

**双视图切换：今日作业与经营概览。**

今日作业为左右两栏。左栏承载指标达成进度、品类签约矩阵、今日三件事与异常预警；
右栏为商家名单与商品名单，支持排序、搜索与行内展开。

经营概览为自上而下的七段结构，每段标题下附一句该段回答的业务问题。

### 技术要点

图表均为内联 SVG 手绘，不引入图表库，以保持单文件自包含。

**空态分两种语义且不可共用同一文案。**「本商圈尚无已签商家，预警不适用」与
「已逐家检查，未发现异常」是不同的结论，前者说明检查条件不成立，后者说明检查已完成。

**「待催上架」不设为预警类型。** 门槛放开后八成以上已签门店都会命中，
其性质是作业名单而非异常信号。

## 05 业务助手（无界面）

### 解决什么业务问题

一线角色每日需要的是单个数值与一句可直接转述的结论，而非完整报表。
但同一个「保本线」存在三种算法，结果相差可达三成。若由助手自行计算，
采用哪一种取决于提问措辞，同一使用者连续提问两次可能得到不同答案。

### 核心设计

| 设计点 | 说明 |
|---|---|
| 计算与表述分离 | 助手不承担计算，只负责表述。两个助手与工具页共用同一份引擎 |
| 提示词四层分层 | 平台、助手、技能、会话四层，冲突判定固化在助手层，会话层无权改动口径 |
| 口径随数返回 | 取数脚本的返回值自带口径说明，助手须连同口径一并转述 |
| 假定值强制标注 | 未标注假定值等同于将估算值作为实测值对外输出 |
| 双层用例 | 红线用例约束行为，锚点用例校验数值，未通过不予出包 |
| 角色包六件 | `role.json` `SOUL.md` `AGENTS.md` `TOOLS.md` `BOOTSTRAP.md` `HEARTBEAT.md` |

该模块无界面，其设计价值在于结构而非对话窗口，故以目录组织、配置文件与用例集呈现，
不构造演示性质的对话界面。完整说明见 [`agents/README.md`](agents/README.md)。

## 06 开航排期推演台

### 解决什么业务问题

实测样本量不足以作为基准，跨城开航顺序只能凭经验排布，排定后无从复核。
更关键的是，「该点位是否划算」与「该点位何时开始划算」是两个不同的问题，
混同表述会导出错误结论。

### 核心功能

| 功能 | 说明 |
|---|---|
| 双指标并列 | 静态账过线与梯队转正分开给出，不合并为单一评分 |
| 六十个月逐月推演 | 由覆盖爬坡与选择率爬坡两条曲线驱动，营销补贴按站龄递减 |
| 开航梯队与逐年排期 | 梯队分五档，排期受逐年产能上限约束，观察池不进入排期 |
| 候选点位明细 | 支持排序，展开单行可查看该点位六十个月轨迹，含当月利润与累计现金两条线 |
| 地图视图 | 候选点位按订单池决定点径、按梯队决定颜色，两个维度不相互覆盖 |
| 三档选择率并列 | 主档取中值，高低两档同屏给出以呈现区间 |

**双指标为什么不能合并：**

- **静态账过线**回答稳态水位下该点位的月度账能否打正，属终局判断。
- **梯队转正**回答自开航起第几个月当月利润转正，属过程判断。
- 同一点位可能静态账过线却在推演期内不转正，原因是爬坡过慢。合并为单一评分会
  同时丢失这两个信息。

### 界面上能看到什么

**双视图：排期与地图。**

排期视图自上而下依次为：三张判决卡、双指标口径说明、开航梯队五档、逐年排期表、
候选点位明细表与轨迹卡、模型公式链六段、假定值一览（逐条标注待校准）。

地图视图呈现全域候选点位分布，右栏为分城汇总与选中点位的轨迹。

### 技术要点

这条线与单城那条线**刻意不耦合**：取数范围与半径口径都不一样，混用会得出假的口径一致。
排期是白名单先落位再逐年贪心，白名单不过经济性闸也占一个产能名额，
占位不占名额会让产能闸形同虚设。

## 数据说明

### 数据边界

哪些是公开数据可以直接用、哪些必须生成，这条界线本身就是做数据产品的基本功：

| 数据 | 来源 | 本项目怎么处理 |
|---|---|---|
| 地图底图 | 公开地图服务 | 直接使用，署名常驻 |
| 公网 POI（餐饮、住宅、商场、学校） | 公开地图数据 | 按同一形态**生成同量级的点** |
| 起降点坐标 | 属业务数据 | **虚构生成** |
| 商圈围栏边界 | 属业务数据 | **虚构生成** |
| 空域限制分区 | 属公告数据 | **虚构生成**，不对应任何真实公告 |
| 订单起讫分布与时段 | 属业务数据 | **全部生成** |
| 商家签约状态、覆盖率、销量 | 属业务数据 | **全部生成** |
| 商家名与商品名 | 属业务数据 | **程序生成的占位名** |
| 成本科目、客单价、保本线 | 属业务口径 | **虚构取值** |

### 生成时怎么保留分布形态

只替换数值，不替换分布形状。热力图与排行榜的形态由此与真实业务一致：

| 维度 | 生成方式 | 为什么 |
|---|---|---|
| 订单时段 | 双峰分布，午高峰加晚高峰，晚峰更高 | 均匀分布不具备真实需求的节律特征 |
| 配送距离 | 对数正态，中位数约 5 km，长尾到 15 km 以上 | 近距订单占多数，长尾延伸至远端 |
| 商家销量 | 幂律长尾 | 头部少数商家贡献大部分销量 |
| 订单空间分布 | 几个商业核心加一串卫星热点，按距离衰减 | 城市订单按商业密度聚集，非均匀铺开 |
| 供给漏斗 | 逐级留存率不同，签约最难、动销最差 | 逐级留存差异正是该业务的实际卡点所在 |
| 候选点位订单池 | 幂律 | 少数点位贡献大部分订单，长尾点位在任何参数下均不成立 |
| 同城租金 | 跨度接近三倍 | 同城商业地产租金本身即存在数倍差异 |

量级锚点集中在 `scripts/gen_mock.py` 的 `SCALE` 常量中，覆盖数据窗口、全城完单量、
客单价、出单商家数、两类 POI 数量、免配占比、商圈数与开航候选点位数。
**该常量只锚定数量级，具体数值仍由随机过程产生，且刻意与任何真实业务的取值错开。**

随机种子固定，每次生成结果一致，演示可复现；通过 `--seed` 可切换为另一组数据。

### 生成器怎么跑

```bash
python3 scripts/gen_mock.py            # 生成到 site/data/
python3 scripts/gen_mock.py --seed 7   # 换一组数
```

生成后会打印一份自检摘要：各商圈的订单池与保本线、两条漏斗的逐级留存、开航梯队分布。
分布形态异常可由该摘要直接判断。

## 本地运行

```bash
git clone <repo>
cd drone-ops-demo

python3 scripts/gen_mock.py      # 生成演示数据到 site/data/
python3 -m http.server 8080 --directory site
```

浏览器打开 <http://localhost:8080>。

**仓库不收录数据文件。** 未运行生成器时，页面会提示演示数据尚未生成，并给出对应命令。

改了测算引擎之后要重新注入：

```bash
python3 scripts/inject_ue.py            # 注入至三个引用引擎的页面
python3 scripts/inject_ue.py --check    # 只检查一致性，不一致非零退出
```

## 技术栈

纯静态前端，原生 JavaScript，只有选址沙盘与排期推演台的地图页从 CDN 引 Leaflet，
其余页面零第三方依赖，图表全部内联 SVG 手画。数据生成只用 Python 标准库。

选这套的原因很直接：演示站要能被任何人在任何环境跑起来，不需要装环境、不需要构建步骤，
单个 HTML 文件双击就能看。

五个页面共用一份主题令牌（深色为基准，浅色只覆盖取值），共用一份测算引擎，
共用 `localStorage` 里的同一个主题键，切一次全站随身。
